# Lab 4 Test Plan & Traceability Matrix

## 1. Test Strategy & Methodology
Sprint 4 follows **Specification-Driven Development (Spec DD)**, **Test-Driven Development (Test DD / TDD)**, and systematic end-to-end regression hardening.

### 1.1 Required Test Types & Layers
In accordance with Section 10 of the Sprint 4 handout (`SE+Lab+4.pdf`), the test plan explicitly covers all ten required testing types across their authentic operational layers (106 unique Test IDs total):
1.  **Unit Tests (3 tests):** Pure in-memory calculation helpers, date boundary math, and dashboard queue aggregation algorithms (`DASH-02`, `DASH-07`, `DASH-08`).
2.  **API / Integration Tests (40 tests):** Supertest HTTP assertions verifying endpoints, payload validation, atomic conditional updates (CAS), mandatory and optional idempotency keys, revision history, and health check probes (`ACT-01`–`ACT-07b` [8], `CON-01`–`CON-08` [8], `IDEMP-01`–`IDEMP-09` [9], `REV-01`–`REV-06` [6], `DASH-01`, `DASH-03`–`DASH-06`, `DASH-09`, `DASH-10`, `DASH-12` [8], `REG-03` [1]).
3.  **UI Component Tests (15 tests):** React Testing Library tests verifying rendering, user interactions, form validation, error preservation on 409 conflict, revision history modal states, and status workflow controls (`UI-ACT-01`–`UI-ACT-07` [7], `UI-WF-01`–`UI-WF-03` [3], `UI-DASH-01`–`UI-DASH-05` [5]).
4.  **UI Style Tests (3 tests):** Programmatic inspection of Zen Green CSS tokens, badge color classes, modal keyboard focus trapping, Escape key dismiss, and ARIA attributes (`UI-STY-01`, `UI-ACC-01`, `UI-ACC-02`).
5.  **Responsive Tests (1 test):** Verification of layouts and interactions across Desktop (1200px), Tablet (800px), and Mobile (400px) viewports without horizontal clipping (`E2E-05`).
6.  **Authorization Tests (6 tests):** Explicit verification of the Authorization Matrix, 401 unauthenticated, 403 forbidden, and 404 non-enumeration policies (`ACT-08`–`ACT-12`, `DASH-11`).
7.  **Workflow Tests (28 tests):** Permitted status transitions across the 13-row matrix (including exact source-target owner validation and outgoing transitions from `Reopened`), Resolution Gate enforcement (action count only), comment-driven auto-transitions, and advisory resolution behavior (`WF-01`–`WF-10`, `WF-10b`, `WF-11`, `WF-12`, `WF-13a`–`WF-13d`, `WF-14`, `WF-15`, `WF-16` [20 tests] plus `CMT-01`–`CMT-08` [8 tests]).
8.  **Migration / Regression Tests (5 tests):** Verification of database schema alterations, audit retention (`onDelete: Restrict`) on `ActionTaken` and `ActionTakenRevision`, legacy `resolvedAt = NULL` backfill behavior, and full historical regression suites (`MIG-01`–`MIG-03`, `REG-01`, `REG-02`).
9.  **Performance-Smoke Tests (1 test):** Latency benchmarks ensuring dashboard queries and ticket detail loads complete within target thresholds (< 500ms) with 100+ seeded tickets (`SMK-01`).
10. **End-to-End (E2E) Tests (4 tests):** Multi-role Playwright browser automation simulating complete service desk journeys (`E2E-01`–`E2E-04`).

**Total Unique Test IDs: 3 + 40 + 15 + 3 + 1 + 6 + 28 + 5 + 1 + 4 = 106 Unique Tests.**

## 3. Test Safety, Database Isolation & Execution Rules
1.  **Dedicated Disposable Test Database & Environment Isolation:**
    *   All integration and workflow tests must execute exclusively against a dedicated, disposable PostgreSQL test database instance (e.g. ephemeral containerized PostgreSQL created specifically for the test run).
    *   No production, staging, or shared development database may ever be used for integration testing.
    *   Database disposal (dropping or recycling the ephemeral test database container/instance) occurs strictly at the external test environment / CI orchestration level *after* the entire test suite has finished execution.
    *   Individual test files and lifecycle hooks must never run `prisma migrate reset`, drop tables, or alter schema during the test run.
2.  **Append-Only Preservation & Multi-Layered Protection Mechanisms:**
    *   `ActionTakenRevision` records are strictly append-only and immutable across distinct, layered protection mechanisms:
        *   **Row-Level Database Trigger:** `trg_prevent_action_taken_revision_mutation` executes `BEFORE UPDATE OR DELETE` on each row, rejecting row mutations with a trigger exception (`'ActionTakenRevision records are append-only and cannot be updated, deleted, or truncated.'`).
        *   **Statement-Level Database Trigger:** `trg_prevent_action_taken_revision_truncate` executes `BEFORE TRUNCATE`, rejecting table truncations with a trigger exception when attempted by a permitted non-owner role.
